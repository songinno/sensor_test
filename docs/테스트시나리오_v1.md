# 백그라운드 걸음 수 측정 PoC 테스트 시나리오 (v1.0)

> **개정일**: 2026-10-28 · **기반 가이드**: `걸음수측정_테스트가이드_v5.md`  
> **목적**: 배터리 "제한 없음"(원탭 팝업) + WorkManager 15분 주기 + 실행 시 short `health` 타입 FGS 승격 방식으로, 앱 종료 및 화면 꺼짐 상태에서도 걸음 수 센서(`TYPE_STEP_COUNTER`)를 안정적으로 읽을 수 있는지 검증한다.

---

## 1. 테스트 전 사전 준비 (공통 절차)

테스트 시작 전 아래 순서대로 앱 초기 설정을 완료합니다.

1. **앱 실행** ➔ 화면 하단 **`로그 지우기`** 클릭 (이전 로그 삭제)
2. **`1. 신체 활동 권한`** 버튼 탭 ➔ **허용**
3. **`2. 알림 권한`** 버튼 탭 (Android 13+) ➔ **허용**
4. **`3. 배터리 제한 없음 요청(원탭)`** 버튼 탭 ➔ 시스템 팝업에서 **허용**
5. **`4. '사용하지 않는 앱 관리' 끄러 가기`** 버튼 탭 ➔ 스위치 **OFF (비활성화)**
6. 화면 상단 상태가 아래와 같이 표시되는지 확인:
   - `배터리 제한 없음: 예`
   - `사용하지 않는 앱 관리: 꺼짐(정상)`
7. **`5. 주기 작업 등록(15분)`** 버튼 탭
8. **`6. 지금 1회 실행`** 버튼 탭 ➔ 하단 로그에 `steps=숫자`, `fgs=OK` 찍히는지 확인

## 2. 상세 테스트 시나리오 목록

> **주요 판정 원칙**: `ver=5`이고 `src=periodic`이며, 앱을 떠난 지 5분 이상 지난 줄(`sinceAppMin ≥ 5`)만 백그라운드 성공 판정 대상으로 사용합니다. (`src=once` 및 `sinceAppMin=FG`는 제외)

| **SC-01** | **포그라운드 점검** | 앱이 화면에 열려 있을 때 코드나 센서 권한 자체에 기본적 오류가 없는지 사전 검증합니다. | 앱 화면을 켜 둔 상태에서 `6. 지금 1회 실행` 버튼 클릭 | • `steps=숫자`<br>• `fgs=OK`<br>• `sinceAppMin=FG` | 정상 동작 |

| **SC-04** | **타 앱 센서 영향 배제 (핵심)** | 다른 만보기 앱(카카오페이 등)이 센서를 계속 켜둔 덕분에 우리 앱이 얼떨결에 값을 얻는 착시를 방지하기 위해, 타 만보기 앱을 모두 끌 상태에서 독립 수신 가능 여부를 검증합니다. | 설정 ➔ 앱 ➔ 타 앱(카카오페이 등) **강제 중지 후 dumpsys sensorservice 저장** ➔ `step_counter` 연결 목록 기록 ➔ 앱을 닫고 2~3시간 대기 | • 카카오페이 등 타 앱 센서 연결 제거 확인<br>• 다른 앱이 센서를 켜두지 않아도 `steps=숫자` 수신 | **카카오 연결 없음 + 남은 클라이언트 기록 (`FaultDetector` 등)** |
| **SC-05** | **밤샘 미충전 방치 (Doze)** | 폰이 밤새 충전 없이 놓여 있을 때 진입하는 '깊은 절전 모드(Doze)'에서도 주기 작업이 막히지 않고 수집되는지 검증합니다. | 충전기 미연결 상태로 밤새(6~8시간) 방치 후 아침 로그 확인 | • Doze 모드에서도 작업 실행<br>• `doze=true` 줄에서도 `fgs=OK`, `steps=숫자` | **성공 (Pass)** |
| **SC-06** | **밤샘 충전 방치** | 충전기를 꽂아 두었을 때는 절전 제한이 완화되므로, 미충전(SC-05) 상태와 실행 주기를 비교 분석하기 위해 수행합니다. | 충전기 연결 상태로 밤새 방치 후 아침 로그 확인 | • SC-05 대비 주기 실행 간격 안정성 비교 | **성공 (Pass)** |
| **SC-07** | **기기 재부팅** | 폰이 재부팅된 후 사용자가 앱을 다시 실행해 주지 않더라도, OS에 의해 주기 작업이 알아서 재개되는지 검증합니다. | 기기 재부팅 후 앱을 열지 않은 채 1시간 대기 후 로그 확인 | • 부팅 후 앱 미실행 시에도 주기 작업 자동 재개<br>• `uptimeMin` 초기화 및 `steps` 수신 | **성공 (Pass)** |

| **SC-09** | **걸음 수 정확도 (백그라운드)** | 앱이 닫혀 있고 리스너가 꺼져 있던 동안에도 하드웨어 칩 카운터가 누락 없이 걸음 수를 지속 센싱하는지 확인합니다. | 앱 닫고 5분 뒤 주기 로그 확인 ➔ **200걸음 세며 걷기** ➔ 다음 주기 로그 대기 | • 두 주기 로그의 `steps` 차이가 **200 ± 20걸음 이내** | 오차 ±10% 이내 |
| **SC-10** | **알림 노출 관찰** | 백그라운드 수집 시 수 초 이내(실측 readMs 3~13ms)로 포그라운드 서비스(FGS)로 승격될 때, 상단 알림창에 사용자 눈에 띄는 팝업 알림이 상주하여 불편을 주지 않는지 확인합니다. | 설정 ➔ 알림 ➔ 고급 ➔ **알림 기록 ON** ➔ SC-02 수행 후 알림 기록 확인 | • Android 12 이상에서 FGS 알림("걸음 수 확인 중") 상주 안 함 | **성공 (알림 미상주)** |

| **SC-13** | **비삼성 폰 (선택/우선순위 낮음)** | 픽셀 등 삼성 외 타 제조사 폰에서 시스템 클라이언트가 없을 때 첫 읽기 시간과 걸음 카운터 유지 여부를 확인합니다. | 비삼성 폰에서 SC-04(독립수신) 및 SC-09(백그라운드 정확도) 수행 | • 시스템 클라이언트가 없는 순수 하드웨어 칩 상태에서 첫 `readMs` 측정<br>• 카운터 연속성 검증 | `steps=숫자` 수신 및 지연시간 기록 |

> **참고**: 현재 PoC 테스트 앱은 서버 전송 로직이 포함되지 않아 실제 앱보다 소모량이 적게 나옵니다. 차후 서버 전송 네트워크 로직 결합 후 2차 실측을 진행합니다.

## 3. 로그 꺼내기 및 검증 명령 (ADB)

PC 터미널(CMD/PowerShell)에서 실행하여 측정 결과를 추출합니다.

```bash
# 1. 내부 저장소의 probe.log 파일을 PC로 가져오기
adb shell run-as com.example.sensor_test cat files/probe.log > probe.log

# 2. 실시간 로그캣 확인
adb logcat -s StepProbe

# 3. 앱 대기 버킷 확인 (5 = EXEMPTED가 정상)
adb shell am get-standby-bucket com.example.sensor_test

# 4. 배터리 최적화 화이트리스트 등록 여부 확인
adb shell "dumpsys deviceidle whitelist | grep sensor_test"

# 5. 센서 서비스 상태 기록
adb shell dumpsys sensorservice > ss_output.txt
```

## 5. 최종 판정 및 차후 조치

| 측정 결과 | 원인 해석 | 차후 개발 반영 조치 |
|---|---|---|
| **SC-02·03·04 판정 줄 대부분 `fgs=OK` + `steps=숫자`, 평균 간격 15~30분** | **D안 수집 방식 1차 통과 (주간 수집)** | SC-05·09·10·11과 구형 갤럭시(SC-12) 확인 후 수집 방식 최종 확정 |
| **SC-02 성공, SC-04에서 TIMEOUT** | 타 앱(카카오 등)이 센서를 켜 둔 영향이었음 | 센서 수신 samplingPeriod 및 타임아웃 시간 재조정 |
| **`exempt=true`인데 `fgs=DENIED`** | 배터리 원탭 예외가 FGS 백그라운드 승격으로 미인정 | 삼성 배터리 화면에서 수동 "제한 없음" 지정 안내 추가 |
